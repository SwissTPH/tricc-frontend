## Part I — Business description

### What this is

A way to *run* the guideline you are authoring: answer the questions as a health worker would,
watch which questions appear and which are skipped, and see which diagnosis you arrive at.

### Why it matters more than any explanation

Every abstraction in TRICC — relevance, decision gates, scoring, skip logic — becomes obvious the
first time you watch a question disappear because of an answer you just gave. No paragraph of help
text achieves that. For the goal in `20260825-guided-authoring.md` — an open-minded clinician doing
the clinical authoring — this is the single most effective teaching mechanism available.

It is also the only honest way to check a guideline does what its author intended. Today the check
is: convert, deploy to a phone, and click through 300 questions by hand. That happens rarely, so
mistakes are found by health workers.

### The constraint

The logic that turns a diagram into a runnable form lives in `tricc_oo`, in Python. The authoring
tool runs in a browser with no server. It cannot execute Python.

Reimplementing TRICC's transformation in JavaScript would give a genuinely live preview — edit a
node, see the change immediately. It is also a very large piece of work, and worse, it would be a
**second implementation of the thing that defines what a guideline means**. Two engines that
disagree is a worse failure than no preview.

So preview works differently: the guideline is converted by `tricc_oo` into a runnable artifact,
and the tool renders that artifact. The rendering is fully in-browser, because the form runtimes
are themselves JavaScript. What preview needs is a route to run the conversion.

### Honest consequence

Preview is **not live**. There is a build step between editing and previewing, and it needs
`tricc_oo` reachable — as a command you run yourself, as a small local helper, or, later, as part
of a hosted service. In a purely offline browser with no Python anywhere, there is no preview.

That is a real limitation and it is stated up front rather than discovered.

## Part II — Technical specification

### 1. Shape

```
project ──► [ tricc_oo conversion ] ──► artifact ──► [ in-browser runtime ] ──► preview session
             (Python, out of browser)                 (JavaScript, in browser)
```

Only the middle arrow is environment-dependent. It is a port; everything else is shared.

### 2. `PreviewPort`

```ts
interface PreviewPort {
  readonly available: boolean
  readonly kind: PreviewKind          // 'xform' | 'html'
  build(project: Project, opts?: BuildOptions): Promise<PreviewArtifact>
  describe(): { how: string; requires: string }   // shown when unavailable
}
```

Adapters:

| Adapter | How it converts | Where |
|---------|-----------------|-------|
| `ManualPreview` | The author exports, runs `tricc` themselves, and drops the artifact back into the tool | Always available; zero infrastructure |
| `CompanionPreview` | POSTs the project to a small local HTTP helper wrapping `tricc_oo` | Local, opt-in, configured by URL |
| `HostedPreview` | Server-side conversion | A hosted shell, later |

`ManualPreview` exists so preview is never wholly unavailable, and so the artifact route is
exercised from day one without anyone having to install a helper. `describe()` supplies the exact
command to run, with the project's own paths filled in — a copyable line, not a documentation
reference.

The companion helper is a thin wrapper (`tricc` + an HTTP endpoint + CORS), specified separately
if this route is chosen. It is deliberately not part of the browser application.

### 3. Open decision — which artifact

**This is the one thing this spec does not settle, and it should be settled before implementation.**

| Route | Artifact | Runtime | Assessment |
|-------|----------|---------|------------|
| **A. XForm** | XLSForm → XForm XML | **Enketo** or **ODK Web Forms** — both JavaScript | The XML already exists: `pyxform` converts it during validation (`xlsform_cht.py:843`, `convert_result.xform`), so no new conversion is needed. Highest fidelity — it is literally the deployed artifact. Cost: embedding a substantial third-party runtime, and its data model must be fed and read. |
| **B. HTML** | `HTMLStrategy` output | An iframe | Simplest by a distance — self-contained HTML + JS, render it and it works. Lowest fidelity: a preview-grade renderer, not what gets deployed, so behaviour may differ from the field. |
| **C. FHIR SDC** | Questionnaire + CQL | FHIR-Core / Android | **Not viable.** The Kotlin engine is not working yet. Recorded so it is not re-proposed. |

Route A is the more valuable and the more expensive. Route B is deliverable quickly and would
prove the whole pipeline — port, build, artifact, session — at low cost.

**Recommendation:** build the port and the session model against **B** first, since they are
route-independent, then add **A** as a second `PreviewRuntime` once the shape has proven itself.
The runtime is an interface (§4) precisely so this is an addition rather than a rewrite.

### 4. Runtimes

```ts
interface PreviewRuntime {
  mount(el: HTMLElement, artifact: PreviewArtifact): Promise<PreviewSession>
}

interface PreviewSession {
  readonly state: Observable<PreviewState>   // visible questions, answers, reached outcomes
  answer(field: string, value: unknown): void
  reset(): void
  trace(field: string): FieldTrace | undefined
  dispose(): void
}
```

Both runtimes are sandboxed in an iframe. Generated form JavaScript is not trusted with the
authoring document, and the boundary keeps a runtime's global state from leaking into the app.

### 5. Traceability — preview to diagram

What makes this a teaching tool rather than a demo: **every previewed field links back to the node
that produced it, and every hidden field explains why it is hidden.**

`../../tricc_oo/feature/test-spec-strategy.md` already provides exactly this. `TestSpecStrategy`
emits `<form_id>.form-model.json` keyed by post-mangling export name, carrying question↔answer
linkage, graph structure and expression provenance — its own example is *"`other_dis` was hidden;
its relevance depends on `cesi_type`, which was `["blindness"]`"*.

So:

- Preview builds request `-T TestSpecStrategy` alongside the chosen output strategy.
- The form model maps export names back to node ids, giving click-through from a previewed field to
  its node on the canvas.
- Hidden fields are listed with the reason: which relevance hid it, which concepts that depends on,
  and their current values.
- Reached `end` nodes and diagnoses are highlighted on the canvas as the session progresses.

This is the difference between "the form ran" and "I understand why my logic did that". It is
worth treating as a requirement, not a refinement — and it costs one extra strategy flag because
the work already exists in `tricc_oo`.

### 6. Staleness

The artifact is a build, so it goes stale the moment the project is edited.

- Every session shows the document version it was built from.
- Editing while a preview is open marks it stale, visibly, without closing it — an author
  comparing preview against diagram is doing exactly the right thing and must not be interrupted.
- Rebuild is explicit. Nothing auto-rebuilds, since a build is slow and may need the author to run
  a command.
- Answers entered are retained across rebuild where field names survive, so an author iterating on
  one branch does not re-answer twenty questions each time.

### 7. Export coupling

Preview builds are ordinary exports plus `-T TestSpecStrategy`. That means preview exercises the
real export path, so a project that previews is a project that converts. The same validation gates
apply — a guideline with errors or CQL profile violations cannot be previewed, for the same reason
it cannot be exported.

### 9. Tests

**Unit** — `form-model.json` parsing and export-name → node-id mapping, including mangled names
with `_Vv_`, `_Ii_` and `_Rr_` suffixes; session state transitions; staleness on document change;
answer retention across rebuild.

**Component** — trace UI explains a hidden field from a fixture form model; clicking a previewed
field selects its node; stale banner appears on edit without closing the session.

**E2E** — `ManualPreview`: export, load a pre-built fixture artifact, answer through a branch,
watch a question disappear, click it back to the canvas. Uses a committed artifact, so it needs no
Python.

**Contract** — the fixture artifacts are regenerated by the `tricc_oo` contract job
(`20260825-local-app.md` §8), so a change to `form-model.json`'s schema breaks this repo's CI
rather than the preview silently.

### 10. Acceptance criteria

- [ ] `PreviewPort` isolates the only environment-dependent step; the session and UI are
      adapter-independent.
- [ ] `ManualPreview` works with no helper installed, and `describe()` gives a copyable command.
- [ ] A previewed field links back to its node on the canvas.
- [ ] A hidden field explains why, naming the concepts its relevance depended on and their values.
- [ ] Reached ends and diagnoses highlight on the canvas.
- [ ] Staleness is visible and never interrupts; rebuild is explicit; answers survive it.
- [ ] Preview is blocked by the same validation gates as export.
- [ ] Runtimes are iframe-sandboxed.
- [ ] Where preview is unavailable, the UI says so and says what would enable it.

### 11. Implementation phases

1. `PreviewPort`, artifact/session types, `form-model.json` parsing and name mapping.
2. `ManualPreview` + Route B runtime — proves the whole pipeline cheaply.
3. Trace UI, canvas linking, outcome highlighting.
4. Staleness and answer retention.
5. `CompanionPreview` (needs its own small spec for the helper).
6. Route A runtime, **if** §3 resolves that way.

### 12. Open risks

**§3 is unresolved.** Everything here is designed to survive either answer, but building the wrong
runtime first wastes real effort. Resolve before phase 2.

**A JavaScript TRICC engine remains the thing that would make this genuinely live**, and it is not
being ruled out — only deferred as too large for v1, and dangerous as a *second* definition of
guideline semantics. If it is ever built, the honest framing is that it becomes the reference and
`tricc_oo` validates against it, or vice versa. It should never be two peers.
