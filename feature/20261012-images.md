## Part I — Business description

Guidelines show pictures: a child with chest indrawing, a MUAC tape on the red band, a rash.
Today the editor cannot hold them. A draw.io import loses them, and a YAML project cannot carry
them at all.

### The image library

A project has **one image library**: a **Media** tab next to Processes, Activities and Dictionary.
It shows every image as a thumbnail with its name, size, and the concepts that use it. From it an
author can:

- **add** images (button or drop files on the tab);
- **rename** one (its name is its id; the concepts that use it follow);
- **replace** its picture, keeping its name and every use;
- **delete** one, after a confirmation that lists what uses it.

An image is **made smaller when it is added** if it is wider than the *maximum image width*
preference (default 800 px). Large phone photos would otherwise make the form heavy to download
on a health worker's device. SVG drawings are kept as they are.

### Images belong to concepts

An image is **part of a text**: the questionnaire text (q-display), the hint or the help of a
concept, at the place the author puts it, like bold or a list. "Look at the chest: [picture] Is
there indrawing?" is one text. Because texts belong to concepts and the dictionary is project-wide,
every question and answer bound to that concept shows the picture, in every activity. A node never holds an image itself (the YAML stays codes only).

- **In the text editor** (the Format modal of q-display, hint and help), an *Image* button inserts
  a picture at the cursor: pick one from the library or add a new one. Dropping or pasting an image
  file in the editor does the same.
- **Dropping an image file** on a question, an answer row, or a dictionary row puts it at the start
  of that concept's questionnaire text. If there is no questionnaire text yet, one is made from the
  display, then the picture is put in front. If the node has no concept yet, one is created from its
  name, the same as when its text is first typed.
- A node whose questionnaire text has a picture shows the **first one, small, on top of the node**.
  The node keeps its width; the picture is scaled to fit it, at most 48 px high. Answers with a
  picture show a small icon on their row.
- How a form shows a picture is up to each output of `tricc_oo` (Patrick, 2026-10-12: "it could be
  implementation specific, the image too without any special management"). The editor stores the
  picture in the text and nothing else.

### What is exported

The images are files in the project folder and in the exported archive, next to the YAML.
Conversion by `tricc_oo` puts them in the form: an image on a question or answer in XLSForm/CHT, an
item or answer image in FHIR Questionnaires.

### Import from draw.io

Images drawn in draw.io (an image shape linked by an edge to a question or an answer) are put in
the library and attached to that node's concept, instead of being lost.

## Part II — Technical specification

### 1. Files

Images live under `<media_path>/images/<id>.<ext>`. `media_path` is the existing `tricc.yaml` key
(`Project.mediaPath`), default `media`.

- `id` matches `^[a-z0-9][a-z0-9_-]*$`, from the dropped file name slugged and made unique
  (`muac-red.png` → `muac-red`). The file name **is** the id; the extension comes from the content
  type (`png`, `jpg`, `gif`, `webp`, `svg`).
- No manifest file: the library is the folder listing. Width and height are read from the bytes when
  needed (header parse, no decode).

`ProjectFiles` becomes `Record<string, string | Uint8Array>`. Text files stay strings; anything
under `<media_path>/` is bytes. Affected:

- `readProject` / `writeProject` and the incremental diff (byte compare for binaries);
- `toArchive` / `fromArchive` (`fromArchive` keeps media entries as bytes);
- the three persistence adapters: `FileSystemPersistence` (write a `Blob`), `BrowserStoragePersistence` /
  `LocalPersistence` (IndexedDB stores `Uint8Array` as is), `DownloadPersistence`, and the memory
  adapter; `FakeDir` in tests.

### 2. Document model

The images are in the project model and in the Yjs document, as immutable byte values:
`project.images: Record<id, { id, contentType, data: Uint8Array, width?, height? }>`, a `Y.Map` of
`Y.Map`s whose `data` is a `Uint8Array` (Yjs stores it as one binary item, no per-byte cost).

Why not a side store, as first drafted: the bytes are small after the resize (§4), never edited in
place (a replace is a new value), and in the document undo, redo, autosave and the local
collaboration channel handle them with no extra code. A side store needed its own undo, its own
persistence and its own sync. A hosted backend that wants blobs out of the CRDT can move them behind
a content hash later without changing the YAML.

- Mutations: `addImage`, `renameImage` (rewrites every `image` node that refers to it, in every
  designation, in the same transaction), `replaceImage`, `removeImage`. Putting a picture in a text is
  an ordinary designation edit (`withDesignationText`).

### 3. The `image` node in the message AST

`TriccMessage` gets a leaf node:

```ts
{ type: 'image'; src: string; alt?: string }   // src: 'Binary/<id>'
```

- `src` uses the FHIR way of pointing at bytes, a relative reference to a `Binary` by id.
  `tricc_oo` resolves `Binary/<id>` to `<media_path>/images/<id>.*` and, for FHIR output, emits that
  Binary (it already builds Binaries from images).
- It is a block-or-inline leaf, allowed anywhere a `text` node is, including inside list items.
  Not inside a `mark` (a coloured picture means nothing).
- **Markdown** (the designation `value`, read by tools that ignore the extension):
  `![alt](Binary/<id>)`. `toPlain` drops it (the alt text, if any, in brackets).
- **JSON** (the `designation-message` extension) carries it as is, so the AST round-trips.
- `references()` also returns image ids, for validation and for rename.
- `node.media.image` (the current, unused node field) is **read for legacy projects only**: on load it
  becomes an `image` node at the start of the node's q-display (same migration as texts,
  `moveTextsToConcepts`) and is never written. `NODE_FIELDS.media` becomes `custom` (read-only),
  like `form_id`.

Why in the text and not a concept field: the picture is part of what the health worker reads, in a
place in that text; it is translated with the wording (a different picture per language when
needed) with no extra mechanism; FHIR renders it the same way as the rest of the text (`rendering-xhtml`), and
single-picture outputs can still take the first one.

### 4. Upload and resize (editor)

`prepareImage(file, maxWidth)` in `@tricc/editor`:

- accepts `image/png|jpeg|gif|webp|svg+xml`; anything else is refused with a message;
- raster wider than `maxWidth`: `createImageBitmap` (with `imageOrientation: 'from-image'`, so the
  EXIF rotation is applied) → `OffscreenCanvas` (canvas fallback) → re-encode in the same format
  (JPEG/WebP quality 0.9). If the result is larger than the original, the original is kept;
- SVG and animated GIF are kept as they are; never upscaled.

Preference: `EditorPreferences.imageMaxWidth`, default 800, range 100–4000, on the Preferences page.

The project-level `tricc.yaml` `parameters.image_max_width/height` (used by `tricc_oo` when
converting) are unchanged and independent: the preference keeps the library small, the project
caps are the form's rule.

### 5. Editor surfaces

- **Navigator:** a *Media* tab after Dictionary (`onOpenMedia`), rendering `MediaView`: a grid of
  thumbnails (object URLs from the store, revoked on unmount) with name, pixel size, file size, and
  "used by" concept chips that open the concept. Add / rename / replace / delete as in Part I.
  Dropping files anywhere on the view adds them.
- **Rich text editor:** a TipTap `image` node (inline atom, rendered from an object URL of the
  store) mapped to and from the AST in `text/prosemirror.ts`; an *Image* toolbar button opening the
  library picker (search, *Add new*), and file drop/paste handlers that upload then insert.
- **Concept dialog / dictionary rows:** the q-display preview shows pictures; a dictionary row gets a
  thumbnail column (first picture). A file dropped on a row or on the dialog goes to the start of the
  q-display (in the dialog, into the draft, applied on Save).
- **Canvas:** `TriccNode` renders the first picture of the q-display above the label in a box of the
  node's current width and at most 48 px high (`object-fit: contain`). Answer rows show a small image
  icon. Dropping a file on a node or an answer row: `dragover` accepts `Files`, `drop` uploads and
  prepends the picture to that concept's q-display, creating the concept if missing. The node height
  changes, so it goes through the same handle-signature refresh as answers.
- **Answer picker / concept card:** show the thumbnail where they show the display.

### 6. Validation

- `image.missing` (error): a text refers to an image id with no file.
- `image.unused` (info): an image no concept uses.
- `image.too-wide` (warning): wider than the project `image_max_width` when that is set (files added
  outside the editor).

### 7. Draw.io import

Reuse what `tricc_oo` does (`xml_to_tricc.py` `add_image_from_style`): an mxCell with an embedded
`image=data:image/<type>;base64,…` style, linked by an edge to a question or a `select_option`.

- The bytes go to the library, id from the target node's name (`<name>`, or `<name>-<option>` for an
  answer), made unique; resized with the same preference.
- The picture is put at the start of the target's q-display (the concept is created by the text
  migration). The image cell and its edge are not imported as nodes or edges.
- External image URLs in a style are reported (not fetched), as `tricc_oo` does.

### 8. `tricc_oo` (separate spec, other session)

Extends the message-tree spec (`../../tricc_oo/feature/20261008-concept-texts-q-display-and-message-tree.md`):

1. **AST:** an `image` node (`src`, `alt`) in the message model, its Markdown rendering
   (`![alt](Binary/<id>)`) and its JSON form.
2. **YAML input:** images referenced by texts are resolved under `<media_path>/images/` and
   registered in `project.images` (the shape draw.io input already produces).
3. **Outputs:** each output renders the `image` node as suits it (implementation specific, no rule
   from the editor). The first picture of a question's text as `node.image` keeps today's outputs
   working until they do more.

### 9. Tests

- core: `image` node in Markdown/JSON/plain (parity fixtures regenerated with `tricc_oo` once it
  supports the node); file round trip with binaries (folder and archive, byte-equal); legacy
  `media.image` migration; rename rewrites references; validation rules; draw.io image cell import.
- editor: `prepareImage` (resize, keep original when larger, SVG untouched) with a fake canvas;
  concept dialog image row.
- e2e: add to the library, insert from the Format modal picker, drop a file on a node (thumbnail on
  top, node width unchanged), export archive contains the file, reopen keeps it.

## Decisions (2026-10-12)

- Node thumbnail: 48 px high, fixed.
- Pictures are allowed in q-display, hint and help (same editor).
- How an output shows pictures is `tricc_oo`'s choice; the editor has no split or placement rule.
- Bytes live in the document (§2), not in a side store.
